# Querio — Data Requirements

## 1. Overview

Querio needs three distinct categories of data, each with a different owner, source, and lifecycle:

1. **Domain document corpora** — the source-of-truth content Querio retrieves answers from.
2. **Evaluation datasets** — golden Q&A pairs and a labeled routing test set, used to measure quality.
3. **Operational data** — query logs and document metadata, generated by the running system.

## 2. Domain Document Corpora

One curated corpus per domain, stored as chunked, embedded documents in that domain's vector store namespace.

| # | Domain | Example source documents | Notes |
|---|---|---|---|
| 1 | Co-curricular Activities & Clubs | Club charter/list, club joining process docs, event participation rules/circulars | Likely to change per semester (new clubs) — plan for easy re-indexing |
| 2 | Certifications | List of available certifications, eligibility criteria, enrollment/credit-transfer process docs | May span multiple departments — confirm single source of truth with mentor |
| 3 | Extra-Curricular Activities & Sports | NCC/NSS enrollment guidelines, sports trial schedules/rules, cultural event circulars | Some content is time-bound (trial dates) — flag stale documents |
| 4 | Career/Internship/Placement (incl. NOC) | Placement process handbook, eligibility criteria, **NOC application guidelines** (required documents, timelines, contact) | **Guidance-only domain** — corpus must only contain process/policy docs, never anything implying Querio can submit on the student's behalf |
| 5 | Formal Education | Syllabus documents per subject, elective lists, teaching-learning process/academic regulations | Largest corpus likely — consider per-subject sub-organization within the namespace |
| 6 | Leave Management & Attendance | Leave policy document, attendance shortage & condoning rules, application process docs | **Guidance-only domain** — same constraint as D4 |

**For each document, capture at minimum:**
- `domain` (1–6)
- `source_name` (e.g., "Attendance Policy 2025-26")
- `source_type` (PDF, circular, webpage, handbook chapter, etc.)
- `last_updated` / `version`
- `owner/contact` (which department office is the source of truth — useful both for citations and for the "direct student to the right contact" requirement in D4/D6)

**Collection plan:** Phase 0 deliverable is "document collection for all 6 domains." Concretely this means:
1. Identify the department/office that owns each domain's authoritative documents.
2. Collect current versions (not drafts, not last year's if this year's exists).
3. Get mentor/department confirmation that these are the correct, approved sources — especially for D4 and D6, since these are the most policy-sensitive.
4. Convert to a consistent ingestible format (plain text/markdown extraction from PDFs, etc.) before chunking.

## 3. Chunking & Metadata Schema (Vector Store)

Suggested minimum schema per chunk, stored alongside the embedding:

```
chunk_id        string   (unique)
domain          enum     (D1..D6)
source_name     string
source_section  string   (heading/section this chunk came from, for citation)
text            string   (the chunk content)
last_updated    date
embedding       vector
```

Keep `source_name` + `source_section` populated for every chunk — this is what powers Core Feature #3 (Source Citation): every answer must reference the document/section it came from.

## 4. Evaluation Datasets

### 4.1 Golden Q&A Dataset
- Hand-curated question–answer pairs, covering all 6 domains, used to measure retrieval + answer quality (target: ≥85% accuracy).
- Each entry should include: `question`, `domain`, `expected_answer` (or key facts the answer must contain), `source_reference` (which document/section the answer should be grounded in).
- Build this **per domain**, not as one mixed pool — you need per-domain RAGAS scores (Success Criteria requires evaluation "run separately for every domain").
- Include some intentionally ambiguous or edge-case questions (e.g., a question that could plausibly belong to two domains) to stress-test routing, not just retrieval.
- For D4/D6, include questions that probe the guidance-only boundary directly — see `05_evaluation_and_testing.md`.

### 4.2 Routing-Accuracy Test Set
- A separate labeled set: `{query, correct_domain}` pairs, used only to measure the classifier/router (target: ≥90% accuracy).
- Should be broader and more varied in phrasing than the golden Q&A set, since its only job is testing routing, not answer quality.
- Include queries that are deliberately ambiguous between two domains, to test the fallback behavior defined in `02_architecture.md` §2.2.

## 5. Operational Data (generated at runtime)

### 5.1 Query Log DB schema (PostgreSQL — suggested starting point)

```
query_log
─────────
id              serial PK
question        text
matched_domain  enum (D1..D6)
confidence      float          -- router's confidence score, useful for later tuning
resolved        boolean        -- did retrieval find a groundable answer?
top_sources     text[]         -- optional: which document chunks were used
created_at      timestamp
```

Keep this table strictly analytics-only. **Do not** add a `status` field with values like `pending/approved/rejected` — that would reintroduce the workflow-tracking concept that was explicitly removed from scope (see `04_scope_and_guardrails.md`). If department analytics later need more detail, add read-only aggregation fields, not state.

### 5.2 Document metadata table (for Admin Document Management)

```
document
────────
id              serial PK
domain          enum (D1..D6)
source_name     text
source_type     text
version         text
last_updated    date
owner_contact   text
active          boolean        -- lets admin retire a doc without deleting history
```

This is what the admin panel (Nancy's responsibility) reads/writes when adding, updating, or removing documents per domain — the requirement is that this happens without engineering involvement, so the schema should be simple enough to drive a basic CRUD UI.

## 6. Data Ownership & Freshness

- Assign one team member (or rotate) to own each domain's document freshness — stale policy documents (especially D4/D6) are a real risk since NOC/attendance rules can change per semester.
- Document a simple re-indexing process: when a source document changes, re-chunk + re-embed just that document's chunks, don't re-index the whole domain unless necessary.
- For the report/demo, keep a short changelog of when each domain's corpus was last verified against the current official policy — this is useful evidence for the mentor that data isn't stale mock content.
